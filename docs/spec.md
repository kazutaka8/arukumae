## 1. 一言でいうと

風車のブレードのような長い荷物を運ぶとき、**軌跡図にかかる土地（筆）と、切ることになりそうな木を、現地を歩く前に洗い出す道具。**

公図・航空写真・軌跡図を1枚の地図に重ね、かかる筆を計算で拾う。木があるかどうかは、Claude が航空写真を見て区切りごとに判定する。人が画面と現地で確かめて直し、最後に「道路名とキロポスト付きの一覧表」と「現地に持って歩く地図」を出す。

**AI は候補を出し、人が確かめて決める。** この分担を、道具の作りそのものにする。

## 2. 背景

### 2.1 従来のやり方

1. 輸送ルートにかかりそうな地番を調べ、登記情報提供サービスで公図を1件ずつ買う（1件 360円）
2. 座標のない公図は、CAD の上で航空写真や地形図に手で合わせる
3. 軌跡図を重ねた航空写真を紙に印刷し、それを持って現地を歩き、支障になる木を拾う
4. 道路管理者などとの協議では、そのたびに「何キロポストのあたりか」を聞かれ、調べ直す

### 2.2 なぜ今なら作れるか

- 2023年1月から、法務省が全国の公図の電子データ（登記所備付地図データ。地図XML 形式）を無料で公開している。ただし**筆の半分以上は任意座標系で、そのままでは地図に重ならない**
- 2026年2月から、林野庁が全国の森林の GIS データ（森林計画の対象森林の区域、森林資源メッシュなど）を統一の形で公開している
- 国土地理院の航空写真（地理院タイル）は、出典を書けば使える
- 画像を読める Claude なら、航空写真の区切りごとに「木か、木でないか」を理由つきで答えられる

数字と出典は [background.md](background.md) にまとめた。

## 4. 作るもの・作らないもの

**作る：** §5 の機能

**作らない：**

| 作らないもの | 理由 |
|---|---|
| 輸送ルートの選定、本物の軌跡図の作成・修正 | 範囲が広がり、6日で終わらない。軌跡図は受け取ったものを重ねる。ただし、届く前の下調べ用に、車両の寸法から簡易な架空の軌跡図を作る所までは作る（§11.4。軌跡図は届くのが遅く、版もよく変わるため） |
| 電柱・電線・橋梁の判定 | 真上からの航空写真ではほとんど写らない。見落とすと危ないものを AI に任せない |
| 登記の記録の読み取り、相続人の調べ | 個人の情報を外に送ることになる。相続人を確かめるのは専門家の仕事 |
| 協議先の自動の判定 | 長い輸送路では途中で管轄が変わり、状況による所が大きすぎる |
| 交渉の記録、同意書の管理 | 下調べの道具に絞る |
| 届出書・申請書の作成 | 法定の書類を置き換えるものと受け取られないようにする |
| スマホの現地版 | 6日では無理。山の中は圏外も多い。現地は印刷した地図で歩く |

## 5. 機能

優先度：**必**＝3分のデモに要る ／ **望**＝余裕があれば ／ **後**＝ハッカソンの後

| # | 機能 | 優先度 | すること | 受入の条件（デモの舞台で確かめる） |
|---|---|---|---|---|
| F1 | 案件と区間 | 必 | 案件名、輸送の向き、区間（起点・終点）を決める。区間の中の位置は「起点からの距離（m）」で呼ぶ（道路管理者の KP とは別。§8.6） | 舞台の区間（§11）で案件を作ると、起点が 0m、終点が約 1,451m になる |
| F2 | 公図と軌跡図の取り込み | 必 | **公図：** 地図XML の zip（法務省の市町村ごとの zip。中に地図ごとの zip と XML）をそのまま落とすと、展開せずにワーカーで流し読みし、区間の両側 200m の筆だけを残す（§11.3）。任意座標系の地図は読み飛ばして枚数だけ伝える（F4 へ）。**軌跡図：** KML・GeoJSON の線と多角形の縁を全部読み、中心線に投影して「1m ごとの左右の幅」にする（外側線・内側線・多角形のどれで描かれていても同じ扱い）。余裕幅を付ける（初期値は直線 1m、カーブ 2m）。KMZ は解凍して中の KML を読む。軌跡図がなければ、車両の寸法から架空の軌跡図を作る（§11.4） | 架空の軌跡図を KML に書き出して読み直すと、かかる筆の数が同じになる（2026-11-02 に確かめた）。小川村の zip（38MB）をブラウザで読むと、前処理（Python）と同じ筆が残る（2026-11-03。200m の境の 2 筆だけ違う） |
| F3 | 重ね合わせ | 必 | 公図・航空写真・軌跡図・森林の区域を1枚の地図に重ね、表示を切り替える | 舞台で4つが重なり、それぞれの出典が画面に出る |
| F4 | 公図の位置合わせ（案A） | 望 | 座標のない公図（画像・PDF・任意座標系の地図XML）について、まず地番の並びで粗く置き（§16）、Claude が航空写真と見比べて「どの辺りか」の当たりを出す。基準点は人が打ち、残差を見て決める。**提出までには入れない**（2026-11-03 の試し §16） | 任意座標系の地図を、粗い当たりと人の基準点で合わせ、残差が画面に出る |
| F5 | かかる筆を拾う | 必 | 軌跡（＋余裕幅）・伐採範囲と重なる筆を、計算で拾う。AI は使わない | 舞台の区間で、かかる筆が色分けされ、筆数が出る |
| F6 | 木の判定（案C） | 必 | 伐採範囲を区切り、Claude が航空写真から区切りごとに木の割合・針葉樹か広葉樹か・木以外のものを判定する。筆ごとに集計する | 舞台の区間の全区切りに判定が付き、筆ごとの木の面積が出る |
| F7 | 一覧表 | 必 | §9.1 の列で書き出す（Excel か CSV） | 書き出したファイルを開くと、§9.1 の列がそろっている |
| F8 | 持って歩く地図 | 必 | A4 の地図（PDF）。「現地で確かめる所」と書き込む欄を付ける（§9.2） | 舞台の区間で PDF ができ、印刷して読める |
| F9 | 道路名とキロポスト | 必 | 区切り・筆ごとに「道路名・KP（推定）・左右」を付ける（§8.6） | 距離標を2本置くと、全区切りに「小川長野線 ○.○○km 付近」が付く |
| F10 | 人が直す | 必 | 区切りの判定を、画面で人が直せる。直した所は「人」と記録され、地図と一覧に反映される | 1区切りを直すと、地図の色と一覧の値が変わり、「人」と出る |
| F11 | 別の年の写真で見比べる | 望 | 都道府県などの別の年の航空写真（GeoTIFF）を読み込み、2枚を一緒に Claude に見せて「今の割合・前の割合・変化」を判定させる。変化があった区切りは「現地で確かめる所」に入る（§8.4） | 舞台で長野県の 2023年の写真を読み込むと、L053 に「変化あり」が付く |

**遅れたときに削る順：** F4 → F11 → F8 の航空写真の背景（線と色だけにする）→ F8 を1区間だけにする。F5・F6・F10 は削らない（デモの芯）。

## 6. 画面

### 6.1 方針（2026-11-02 に決めた）

**使う人が、使い方から勉強しなければならない作りにしない。** 実務の流れに沿って、触れば分かる画面にする。

- **地図が主役。** 地図を画面いっぱいに広げる。手順・詳細・一覧はどれも地図の上に重ねるパネルにし、開け閉めできる。閉じても中身は消えない
- **実務の流れの順に並べる。** 手順を「1 案件 → 2 取り込み → 3 かかる筆 → 4 木の判定 → 5 確かめて直す → 6 KP → 7 書き出し」と順に並べ、いまどこにいて次に何をすればよいかを一文で出す。前の手順にはいつでも戻れる
- **用地の実務の言葉を使う。** 筆、地番、伐採、距離標、KP など。道具だけの言葉や英語を作らない
- **ボタンには、押すと何が起きるかを書く。** 費用がかかる操作（Claude を呼ぶ）は、押す前に費用の目安を出す（例：「木を判定する（約 $0.3）」）
- **探させない。** 鍵が入っていなければ、判定のボタンの所で鍵の入れ方を案内する。設定の画面を探させない
- **ファイルは地図に落とすだけで取り込む。** 種類（地図XML・KML・GeoTIFF）は道具が見分ける
- **地図の上のものを押せば、その場で分かる。** 筆や区切りを押すと、詳細のパネルに中身（判定・理由・確信）と「直す」が出る
- **地図と一覧はつながっている。** 一覧の行を選ぶと地図がそこへ動き、地図で選ぶと一覧の行が光る
- **「現地で確かめる所」は数を出し、「次へ」で順に見て回れる**
- 色の意味（凡例）を地図の隅に出す（閉じられる）。操作は元に戻せる
- 初めて開いたときは、小川村の見本が入った状態で、全部の手順を触れる
- 事務所の PC が主。ノート PC の画面（1366×768）でも地図が狭くならないこと

### 6.2 割り付け（大枠）

```
┌ 上の帯：案件名・保存の状態・設定 ───────────────────┐
│ ┌ 手順 ┐                                   ┌ 詳細 ┐ │
│ │ 1〜7 │          地図（画面いっぱい）          │ 選んだ │ │
│ │ 次に │                                   │ 筆・  │ │
│ │ する │                                   │ 区切り │ │
│ ├─────┤                                   └─────┘ │
│ │ 一覧 │                                           │
│ │（縦）│                                           │
│ └─────┘                                           │
└───────────────────────────────────────────┘
```

- 手順 2 の「取り込み」では、伐採範囲の決め方（架空の軌跡図を作る・軌跡図のファイルを読む・仮の帯）を選び、車両の寸法や余裕幅を入れて作り直す。結果（掃く幅の最大・区切り・かかる筆の数）がすぐ出る
- 手順（左）・詳細（右）の2つのパネルは、どれも開け閉めできる。一覧は手順の右に縦の列で置き、一覧の要る手順（3〜5・7）でだけ出す。
  幅はドラッグで変えられ、この端末に覚える。一覧は「かかる筆」「確かめる所」のタブで切り替える。
  「確かめる所」には番号を振り、手順 5 の前へ・次へで「3 / 12」のように今どこかが分かる
- 画面の言葉には「?」を付け、載せると説明が出る（区切り・伐採範囲・判定済み・確かめる所・見直し）。文字だらけにせず、意味の分からない言葉も残さない
  - 最初は一覧を下から引き出す形にしたが、一覧の行から飛んだ先の筆を一覧が隠してしまった（2026-11-02 に触ってもらって分かった）。
    地図から飛ぶときは、パネルに隠れていない範囲の真ん中に来るように余白を取る
- 設定（鍵・モデル）と案件の切り替えは、上の帯から開く小さな窓にする。別の画面に移らない
- **タブレット（iPad）**（2026-11-03。現場では iPad が基本だった）：横向き（〜1100px）は手順 250px・一覧 28vw・詳細 300px に詰め、凡例は高さを抑えて中で送る。
  縦向き（〜820px）は手順と一覧を下の引き出し（高さ 46%）にし、詳細は右上、凡例は左へ。地図に現在地のボタン（位置の情報は端末の中だけ）。
  スマホの幅は作り込んでいない（開け閉めはできる）。実機の iPad では未確認（ファイルの保存と公図の zip の読み込みも）

### 6.3 流れ

1. 案件を作る（F1）
2. 公図と軌跡図を地図に落とす（F2）。座標のない公図は位置を合わせる（F4）
3. かかる筆が色で出る（F3・F5）
4. 「木を判定する」を押す（F6）。区切りごとの結果が色で出る。迷う所は上位モデルが見直す
5. 判定を見て、違う所を直す（F10）。「現地で確かめる所」を順に見る
6. 距離標を置く（F9）
7. 一覧表と、持って歩く地図を書き出す（F7・F8）

### 6.4 できたと言える条件

- 開発者以外の人が、説明なしで、小川村の見本から一覧表と地図を書き出すところまで行ける
- 1366×768 の画面で、パネルを全部閉じると地図が画面のほとんどを占める

## 8. 処理の中身

### 8.1 AI と計算と人の分担

| 段階 | Claude | 計算（AI なし） | 人 |
|---|---|---|---|
| 公図を合わせる | 基準点の組の候補（理由つき） | 変換と残差 | 確かめて決める。組を外す・足す |
| 筆を拾う | ─ | 軌跡・伐採範囲と筆の重なり | 余裕幅を決める |
| 木の判定 | 区切りごとの判定（確信・理由つき） | 区切り、面積、集計、森林のデータとの突き合わせ | 画面で直す。現地で確かめて直す |
| キロポスト | ─ | 距離標の間を補間 | 距離標の値を読み、地図に置く |

- **筆を拾うのは計算だけで決める。** 拾い漏れは後で取り返しがつかないので、AI の判断を挟まない。迷う所は「拾う」に倒す（漏れより過剰）
- Claude の判定は、いつも「候補」として扱う。確信が「低」のものと、森林のデータと食い違うものは「現地で確かめる所」に入れる（2026-11-02 に両方入れた。checks.ts で 1 つの並びにし、画面・一覧表・持って歩く地図で同じ順になる）
- 人が直した値は、Claude の判定より優先する。どちらが決めたかを、一覧と地図に出す

### 8.2 座標

- 公図（公共座標系）は平面直角座標系。舞台の長野県は第VIII系（JGD2011。EPSG:6676）。地図XML の座標は **X が北、Y が東**（2026-11-02 に実データで確かめた。区間の起点は X=71,646.4・Y=−45,432.5 になり、公図の道の筆と重なる）
- 換算は国土地理院の式（河瀬の式）。試しの実装で、原点が 0・0、北へ1度が 110,957.2m になることを確かめた。道具の本体では proj4 の EPSG:6676 を使い、同じ点で値が合うことを回帰テストで固定する
- 地図の表示は Web メルカトル、データの保存は緯度経度（WGS84 とみなす。JGD2011 との差は表示の上で無視できる）
- 面積・距離の計算は、平面直角座標系の上で行う

### 8.3 かかる筆を拾う（F5）

1. 「掃く範囲」は、中心線の 1m ごとの点で「左右それぞれ中心線から何 m まで車体と荷物が通るか」として持つ（包絡線）。出どころは3つで、どれも同じ形に落とす
   - 軌跡図のファイル（F2）：線と多角形の縁を 1m ごとに打ち直して中心線に投影し、左右の最大を取る。点のない所は 10m までなら両隣から埋め、それより長く途切れた所は「軌跡図がない」（切らない）
   - 架空の軌跡図（§11.4）：車両の寸法から追従の計算で出す
   - 仮の帯：中心線から一定の幅。軌跡図も車両もないときの代わり
2. 掃く範囲に余裕幅を足す。直線は 1m、カーブは 2m（初期値。人が変えられる）
3. 伐採範囲は、掃く範囲のさらに外側に決めた幅（初期値 3m）を足したもの
4. 伐採範囲と重なる筆を全部拾う。筆ごとに重なる面積（m²）を出す
5. 地番の種類（ふつう・道・水・無地番）で色を分ける。地図では、筆を丸ごと塗らず **伐採範囲と重なる部分だけ** を濃い黄色にする。
   筆を丸ごと塗ると、山林の大きな筆が端だけかかっても全体が黄色になり、「ここも切るのか」と読めるため
6. **「地区外」「別図」はかかる筆に数えない。** 土地ではなく「この地図ではここから先は描いていない（隣の地図を見よ）」という印。
   見本では、隣の地図（-18・-20）の地区外の区画25個のうち20個が、主の地図（-6）に地番のある筆を数十〜百筆ずつ丸ごと含んでいた（2026-11-02 に確かめた）。
   数えると同じ土地が二重に出て、地図も二重に塗られる。地図では灰色の点線だけにし、押すと「隣の地図を見よ」と出す

### 8.4 木の判定（F6・案C）

**区切りを作る（計算）**

- 伐採範囲のうち、**道路の端から外側**を、中心線に沿って 10m ごと×左右に区切る。道路の半幅は設定（初期値 3m）
  - 道路の中心から区切ると、区切りの半分が道路になり、木の割合が読みにくくなるため
- 区切りには「起点から 320〜330m の左」のように呼べる番号を振る（例：`L032`＝320〜330m の左、`R032`＝同じ所の右）
- **急カーブの内側では、区切りが細く潰れて重なる**（試しでヘアピンの内側の `R052`・`R053` がそうなり、Claude が「枠が小さく番号で隠れる」と答えた）。
  2026-11-02 に入れた直し方：内側の区切りの外側の幅を「曲がりの半径 − 0.5m」までに抑える（外側の線が曲がりの中心を越えて折り返さない＝重なった分は中心線に近い所に入るのと同じ）。
  そのうえで面積が 15m² 未満に潰れた区切りは次の区切り（最後なら前）と合わせ、番号は先のほうを残して距離の範囲を広げる（例：`L006` が 60〜80m）。
  30m² にしなかったのは、既定の車両（寝かせたブレード）だと直線の区切りがちょうど 30m²（幅 3m × 10m）で、直線まで合わさってしまうため。番号の札は枠の中ではなく道路の側（枠の道路側の縁から 1.5m 道路へ、道に沿って回す）に置く（2026-11-03。枠の中だと細い区切りの地面を隠すため。判定への効き目は未確認）
- 区切り×筆で面積を出しておく

**Claude に送るもの**

- 区切りの周りの航空写真の切り抜きを、**番号の札がない写真と、札がある写真の組**で送る。札は細い区切りに重なって地面を隠すので、札なしの写真で地面を見て、札ありの写真で番号を対応させる
- 写真は z18（約 0.48m／画素）を3倍に拡大する。拡大しないと 10m の区切りが 20画素ほどしかなく、番号の札が読めない
- 1回に送るのは、写真1組と、道に沿って 200m 分（左右で40区切り）。試しでは入力が約4千トークン、40区切りすべてに答えが返った
- **座標・地名・案件名は送らない。**

**Claude が返すもの**

区切りごとに、決まった選択肢から選ぶ。線や形を描かせず、番号ごとに選ばせる（画像を読む AI が得意な形にする）。

```json
{
  "L032": {"tree": 75, "kind": "針葉樹", "other": ["道路"], "conf": "中", "why": "道の縁まで濃い林冠。手前の 2m ほどは路肩の草"}
}
```

| 項目 | 値 |
|---|---|
| `tree` | 木の割合。0・25・50・75・100 のどれか |
| `kind` | 針葉樹・広葉樹・混じる・分からない・なし |
| `other` | 木以外に写っているもの。道路・草地・畑・建物・設備・水・裸地（複数可。無ければ空） |
| `conf` | 確信。高・中・低 |
| `why` | 理由。短い文 |

- 返ってきた JSON は、端末で形を確かめる（番号の過不足、選択肢にない値）。おかしければその区切りだけ送り直し、それでもだめなら「判定なし」として「現地で確かめる所」に入れる

**判定のあと（計算）**

1. 区切り×筆の面積に木の割合をかけ、筆ごとに「木のある面積（推定）」を出す
2. 森林の区域と突き合わせる。食い違う所（区域では森なのに写真では木がない、など）は「現地で確かめる所」に入れる。もう切られている、太陽光になっている、といった変化の手がかりになる。
   決め方（forest.ts の forestMismatch）：区切りそのものと、道と反対の側と前後に 15m 広げた形の両方が 9 割以上区域の中で、木が 25% 以下 → 「区域なのに木が少ない」。両方が 1 割以下で木が 75% 以上 → 「区域外なのに木が多い」。
   広げた形で見るのは、区域の縁の近く（線が 1/5,000 相当でずれる所）を指摘しないため。見本では 80 区切りの見本の判定に対して 2 区切り（L051・L052）が「区域なのに 25%」になった
   - 区域の縁から 15m 以内は「境界の近く」として、食い違いを指摘しない（区域のデータの細かさの限界で、誤った指摘が出やすいため）
3. 確信が「低」の区切りも「現地で確かめる所」に入れる
4. 高さは写真から分からないので、**木がある区切りはすべて「切る候補」にする**（漏れより過剰）
5. 本数は数えない。山の中では木は1本ずつではなく「面」になるので、面積で示す

**判定のぶれ**

- 同じ写真で何度か（3回を目安）判定させ、区切りごとの一致の割合を計る。期間中に少なくとも1回計り、結果を README に書く（試しの結果は §15）
- ぶれが大きい区切りは確信を下げて扱う（案）

**上位モデルで見直す**

- 全部の区切りを既定のモデル（Sonnet 5.5）で判定したあと、次の区切りだけを上位モデル（既定は Fable 5.1。画面で Opus 5.5 も選べる）にもう一度見せる：確信が「低」、森林の区域と食い違う、別の年の写真で変化がある
- 見直しの答えを採用し、両方の答えを一覧に残す（「Sonnet：25、Fable：100（見直し）」）。食い違いが大きいものは「現地で確かめる所」に入れる
- 試し（§15）では、Sonnet は確信「低」が約17%。区間全体（約 290区切り）なら見直すのは 50区切りほどで、上位モデルの費用は1回あたり $0.3 ほどの見込み（計算）
- 理由：試しで、Sonnet が森の縁の区切りを少なく見た所を、上位モデルと別の年の写真は正しく見ていた。見落としは後で取り返しがつかないので、迷う所だけ上位モデルに任せる

**別の年の写真で見比べる（F11）**

- 区切りの位置は地図の座標で決まっているので、撮影日の違う写真でも同じ区切りを描ける。2枚の写真（それぞれ札なし・札あり）を一緒に送る
- 返させるもの：`tree_now`（新しい写真での割合）、`tree_old`（古い写真での割合）、`change`（変化なし・木が減った・木が増えた・造成や建物の変化・分からない）、ほかは §8.4 と同じ
- 変化があった区切りは「現地で確かめる所」に入れる。木は伸びるし切られもする。写真が古いほど、今の状態とずれる
- 写真が何年のものかを、地図と出力に必ず出す（地理院の「全国最新写真」も場所によって撮影年が違う）
- 写真を道具に取り込むときは、利用条件（出典の書き方、破棄の求めなど）を画面に出す

### 8.5 公図の位置合わせ（F4・案A）

1. Claude に、座標のない公図の画像と、同じ辺りの航空写真の2枚を渡す。どちらも誰でも手に入る公開データ
2. Claude は、両方に写っている目印（道の折れ曲がり、水路の角など）を探し、「公図の点 ↔ 写真の点」の組を、選んだ理由と一緒に返す
3. 計算：組からヘルマート変換（平行移動・回転・縮尺）を求め、組ごとの残差を出す。2組で変換は決まるが、残差を見るには3組以上が要る
4. 残差の大きい組は外せる。合わなければ人が手で点を打つ
5. 点の組が当たらないときは、Claude の役目を粗い合わせ（おおよその位置・向き・縮尺）に下げ、仕上げの点は人が打つ
6. 公図は明治の図面が元のものも多く、ずらして回すだけでは合わない所がある。合わせた結果は「目安」と画面に出す

### 8.6 道路名とキロポスト（F9）

- **道路名：** OpenStreetMap の道路の名前・番号から付ける。「参考」と出す
- **起点からの距離：** 区間の起点（F1）から中心線に沿って測った距離（m）。距離標がなくても、いつも出せる。区切りや筆の位置を呼ぶためのもので、道路管理者の KP とは別。画面と出力では「KP」と呼ばない
- **KP（推定）：** KP は道路管理者が決めた、その道路の起点からの距離で、道ばたの距離標に書いてある。距離標の位置と値は公開データに無いので、次のように推定する
  1. 人が、読んだ距離標を地図の上に置き、値を入れる（2本以上）。**ストリートビューは人が見て読むだけ**にし、画像を道具に取り込んだり Claude に読ませたりはしない（Google の地図サービスの規約が、中身を抜き出して使うことを禁じているため。自分の理解）
  2. 距離標を中心線に投影し、距離標の間を中心線に沿った距離で直線補間する
  3. 一覧には「推定。距離標 12.0〜12.5 から補間」と根拠を出す。距離標の外側は「外挿」と書く
- 距離標の値と実際の距離は、道路の改築などでずれていることがある。補間には、なるべく近い距離標どうしを使う

### 8.7 Claude に送るもの・送らないもの

| 扱い | データ |
|---|---|
| 送る | 航空写真の切り抜き、公図の画像（どちらも公開データ） |
| 送らない | 軌跡図の座標、地名、地権者の情報、案件の名前 |
| ほかに問い合わせる先 | 地理院タイル・林野庁のタイル・OpenStreetMap。表示する範囲は相手に分かる（地図を見るのと同じ） |

- 軌跡図（輸送ルート）は、発注者のまだ公表していない計画であることがある。だから座標を付けずに、写真の切り抜きだけを送る
- 送る前に、何を送るかを画面で見せる（案）

### 9.3 現地マップ（KML・GeoJSON）と、公図を買うリスト

- **現地マップ**（2026-11-03）：かかる筆（かかる部分の形。吹き出しに所在・地番・種類・面積・起点から・KP・木・森林の区域・区切り）、
  区切り（判定の色。白 0% → 黄 25% → 橙 50% → 赤 75〜100%。人が直したものは名前に「人」。吹き出しに判定と理由）、現地で確かめる所（赤い印）、
  中心線と 100m ごとの点（KP つき）、距離標、伐採範囲の外側。フォルダに分け、区切りは最初は畳む。
  なぜ：現場では公図と航空写真を Google Earth に重ねて iPad で見ながら歩いていた（実務でやっていた形）。同じ形で持ち出せれば、それだけで現地の下見に使える。
  運送会社や設計者と重ねるときも KML が通じやすい。航空写真は入れない（Google Earth の写真の上に重ねる）。GeoJSON は同じものを属性つきで（QGIS など）
- **公図を買うリスト**：所在・地番・種類・起点から・左右・KP・かかる面積・森林の区域に、空の「購入」「備考」。同じ所在・地番は 1 行にまとめる。
  登記情報提供サービスで公図や登記事項を 1 件ずつ買うとき（1 件 360 円ほど）の、順と抜けの確認用
- **区切りの詳細に、判定に送ったのと同じ描き方の写真**（札なし・札あり、区切りの周り 25m）を出す。「AI が何を見て決めたか」を人が確かめるため

### 9.4 持ち運びモード（現地の記録）

- 現地で区切りを見て、○（判定どおり）・△（分からない）・×（違う）とメモを残す（2026-11-03）。区切りの詳細の欄で、○△× は押すだけ、メモは入力を離れたときに保存。指で押しやすい大きさ
- **判定（Judgment）とは分けて持つ。** 現地で見たことの記録と、判定を直すことは別の行為で、記録だけ残して帰ってから直すことが多い。× の所は「この区切りを直す」で直す
- 出る所：確かめる所の一覧の「現地」の列（× は赤）、手順 5 の「確かめる所 14 のうち 3 を見た（○ 1・△ 0・× 2）」、一覧表の「現地の記録」の列（筆にかかる区切りの分をまとめる。「L003 ×：電線あり ／ L004 ○」）、
  現地マップの吹き出し（確かめる所の印は、記録があれば緑の丸に変わり、名前に ○△× が付く）、持って歩く地図の表の○×とメモの欄（「× 済」とメモを印字）
- この端末（localStorage）に残す。「現地の記録を全部消す」で消せる
- iPad で使うことを想定した割り付け（§6.2）と現在地のボタンが土台。実機では未確認

## 10. 確かめ方（テスト）

レビューする人がいないので、壊れたら困る計算は回帰テストで固定する。

| 対象 | 確かめること |
|---|---|
| 座標の換算 | 平面直角座標系（第VIII系）↔ 緯度経度が、既知の点で数 cm 以内に合う |
| 筆を拾う | 小さな作り物の筆と線で、重なる筆・重ならない筆・ふちで接するだけの筆が期待どおりに分かれる |
| 区切り | 直線とヘアピンの線で、区切りの数・左右・番号・面積の合計が合う |
| 面積の集計 | 区切り×筆の面積の合計が、伐採範囲の面積と合う |
| Claude の応答 | 番号の過不足・選択肢にない値・壊れた JSON を、取りこぼさずに「判定なし」にできる |
| キロポスト | 距離標2本の間の補間と、外側の外挿の表示 |
| 人が直す | 直した値が Claude の判定より優先され、一覧と地図の両方に出る |

### 11.4 架空の軌跡図

- 本物の軌跡図はないので、区間の中心線と車両の寸法から架空の軌跡図を作る。**道具の本体（ブラウザ）に入れた**（2026-11-02。はじめは Python の前処理の予定だったが、
  軌跡図は届くのが遅く版もよく変わるので、ブレードの長さを入れるだけで作れると実務でも使えると分かったため）。README と動画に「架空」と書く
- 追従の計算：前軸が中心線をたどり、キングピン（駆動軸の真上とみなす）と台車の軸群の中心がそれを追う（引かれる点はいつも引く点の真後ろ、1m 刻み）。
  車両は区間の手前からまっすぐ入り、通り抜けるまで計算する。車体とブレードの縁を 1m ごとに拾って中心線の最寄りの点に投影し、左右の最大を取る。
  角だけでなく縁の途中も拾うのは、ヘアピンの内側ではブレードが弦のように横切り、いちばん内側に来るのが角ではないため
- 車両の型（初期値。案件ごとに運送会社の車両に合わせて直す）。港から積み替え場までの公道では、公道を走れるトレーラーかブレードリフターが多い。
  ヤードの中（公道の外）で使う自走式の多軸台車は、この道具の外（現場の経験から。2026-11-02）
  - **ブレードリフター（公道）**（既定）：トラクタ軸距 4m、キングピン→台車の軸 10m、台車の幅 3m、ブレード 60m・根元の直径 4m・根元はキングピンの 6m 後ろ。
    **既定は寝かせたまま（0°）。** 伐採は安全側に広く出したいため
  - **伸縮トレーラー（公道。ブレードは水平）**：キングピン→後軸 30m、ブレード 55m・根元はキングピンの 3m 前（先は後軸の 22m 後ろ）、立てない
  - 多軸の台車は後輪も操舵するので、実際の切れ込みはこれより小さいことが多い。操舵なしで計算し、広め（安全側）に出す。高さは見ない
- **起立の区間：** ブレードを立てられる所と角度を、場所ごとに人が決める（起点から a〜b m を 60°、のように。数で入れるか、地図で始めと終わりを押す）。
  電線をくぐる所や橋の下では立てられないので、「曲がりなら立てる」とは決めない。どの区間にいるかはブレードの根元の位置で見る。
  重なる区間は新しいほうで上書きする。地図では中心線に沿った青い帯と角度の札で出す。ファイルには書かない（掃く範囲に織り込み済み）
- カーブの判定：前後 5m の向きの差が 6° を超えた所（半径 100m くらいより急）。余裕幅（直線 1m・カーブ 2m）にも使う
- 伐採範囲 = 掃く範囲 ＋ 余裕幅 ＋ 伐採の幅 3m。道路の端（中心線から 3m）より外の部分だけを区切りにする。どの幅も画面で変えられる
- 見本（小川長野線 1,451m）の結果：既定の車両（寝かせたまま）でかかる筆 329。曲がり 820〜920m を 60° に立てると減る。仮の帯（3〜13m）では 331、伸縮トレーラーでは 275
- 掃く範囲と伐採範囲の外側を KML・GeoJSON に書き出せる（Google Earth・マイマップ・QGIS で開ける）。説明に「架空。実在の輸送計画ではない」と入れる。
  読み直すときは「伐採範囲の外側」の線を飛ばす（余裕幅を二重に足さないため）

## 15. 試しの結果（2026-11-02）

案C を、道具の本体を作る前に Python で試した（`experiments/case_c/`。結果の表は `experiments/case_c/out/summary.md`）。

**やったこと：** 区間の2か所（A：起点から 100〜300m、畑と民家。B：500〜700m、森の急カーブ）を、それぞれ左右40区切りにし（道路の端から外側 10m 幅、仮の値）、3つのモデルに各3回判定させた。区切りの判定は §8.4 の選択肢。`effort` は全部 `medium`。

| モデル | 1回の時間 | 1回の費用 | 3回とも同じ答え | 差が25以内 | 確信「高」の割合 |
|---|---|---|---|---|---|
| `claude-sonnet-5-5` | 14秒 | $0.031 | 92〜95% | 100% | 30% |
| `claude-opus-5-5` | 30秒 | $0.080 | 75〜95% | 100% | 25% |
| `claude-fable-5-1` | 39秒 | $0.205 | 68〜92% | 98〜100% | 1% |

- 18回とも 40区切りすべてに答えが返った。拒否はなかった
- 区間全体（約 290区切り、7〜8回）を1回判定すると、Sonnet で約 $0.25、Opus で約 $0.6、Fable で約 $1.5 の見込み（計算）
- **当たり方（Claude Code が拡大した写真で確かめた。開発者の確認はまだ）：** A の木のある3区切り（R016・L020・L021）は3モデルとも拾った。B の急カーブの外側（L050・L051）は、拡大すると大半が樹冠で、**Fable の 100% が近く、Sonnet の 25% は少なかった**（最初は逆に読んでいた。拡大して見直して直した）
- 森の中で影の濃い区切りは、どのモデルも「影で見えにくいが樹冠が覆っていそう」と確信を下げた。仕様どおり「現地で確かめる所」に入る
- A の木（推定）は伐採範囲（試し）約 4,000m² の 5%、B は 92%
- **森林の区域との突き合わせ：** B で4区切り（R051〜R054、急カーブの内側）が「区域外なのに木が多い」になった。写真では森なので、区域の線の細かさの問題と見られる。§8.4 の「区域の縁から 15m は指摘しない」が要ることを確かめた

**撮影日の違う写真で試した（同じ2か所。結果の表は `experiments/case_c/out/summary_multi.md`）**

## 16. 試しの結果（2026-11-03）：案A

座標のない公図を Claude が航空写真に合わせられるかを、時間を区切って試した（`experiments/case_a/`。手順と表は `experiments/case_a/README.md`）。

**やったこと：** 小川村の任意座標系の地図 `20588-1000-1`（大字稲丘、429 筆。ほとんどが山林の筆）を線画（北が上、道は灰色・水路は青、地番、画素の格子）にし、
その辺りの航空写真（地理院タイル z17、約 1.2km × 1.7km、画素の格子）と一緒に Claude に渡して、「公図の画素 ↔ 写真の画素」の組を 3〜6 組、理由つきで返させた。
正解は、同じ大字・地番の筆が公共座標系の地図に 1 つもなかったので（はじめの見立てと違った）、**地番の底（枝番の前の数）が同じ筆**が隣の地図 -6 に 19 あることを使い、
その重心どうしのヘルマート変換で粗く置いたもの（残差 RMS 35m）。

| 回 | 組 | 組ごとの、粗い正解とのずれ | 組から求めた置き場所の、中心の違い | 自己申告の確信 |
|---|---|---|---|---|
| Fable 1回目 | 3 | 17・31・35m | 54m | 低 |
| Fable 2回目 | 4 | 13・120・230・45m | 178m（目盛りを読み違えて縮尺 1.43） | 低 |
| Sonnet 1回目 | 3 | 217・298・240m | 253m（写真の左の水田に重ねた） | 低 |

- Fable は 2 回とも、公図の中央の「道と水路が接する所」を写真の谷筋の分岐に当てた（粗い正解から 13〜17m）。森ばかりの写真でも、手がかりの 1 点は当てられる
- 残りの組はぶれる。3 回とも自分で「確信 低」と言い、「確かめられる地物が乏しい」「別の資料で裏付けを」と書いた。外しているときに外していると言えるのは使える性質
- 粗い正解が ±35m なので、15〜35m の違いは当たりと正解の誤差を分けられない

**決めたこと：**

- Claude の役目は §8.5 の 5 のとおり**粗い当たり**（公図のどのかたまりが写真のどの辺りか）まで。基準点は人が打つ。基準点を Claude に任せる作りにはしない
- **AI を使わない粗い合わせ**も見つかった：任意座標系の地図の地番は、隣の公共座標系の地図の地番の並びの隙間に当たることがあり、枝番違いの筆の重心から ±35m で置けた。地図XML の中だけで試せる。F4 を作るなら、まずこれで粗く置き、Claude の当たりと人の基準点で仕上げる形になる
- 提出までの残りの時間では F4 を道具に入れず、**望のまま**にする。デモでは触れるなら「試した結果」として

## 17. 用語

| 用語 | 意味 |
|---|---|
| 筆（ひつ） | 登記の上での土地の1区画。1筆ごとに地番が付く |
| 公図 | 登記所にある土地の図面。明治の図面が元のものも多く、法務局自身が「おおよその位置と隣接関係を示すもの」と説明している |
| 地図XML | 法務省が公開している公図の電子データの形式 |
| 公共座標系・任意座標系 | 公共座標系の地図は緯度経度に換算でき、航空写真に重なる。任意座標系の地図は、その図面の中だけの座標で、そのままでは重ならない |
| 地区外・別図 | 地図XML で、個々の筆の形が入っていない区画。その地図の外や別の図面を指す印で、土地ではない。隣の地図にはそこに地番のある筆が描かれている |
| 軌跡図 | 長い車両が曲がるときに、車体や荷物が通る範囲を描いた図。外側線・内側線などがある。運送会社が専用のソフトで描き、届くのが遅く版もよく変わる |
| 掃く範囲 | 車体と荷物が通る範囲。この道具では、中心線の 1m ごとに「左右それぞれ中心線から何 m まで」として持つ |
| 追従（トラクトリクス） | 引く点が動いたとき、引かれる点が「引く点の真後ろ、決まった距離」に来るように動く計算。台車の内側への切れ込みを出す |
| オーバーハング | 荷物が車両の前後にはみ出した部分。曲がるときに外へ振り出す |
| 余裕幅 | 軌跡に足すゆとりの幅 |
| 伐採範囲 | 木を切ることになりうる範囲。この道具では、掃く範囲＋余裕幅のさらに外側 |
| 区切り | 伐採範囲を、中心線に沿って 10m ごと×左右に分けたもの。Claude が判定する単位 |
| KP（キロポスト） | 道路管理者が決めた、その道路の起点からの距離。道ばたの距離標に書いてある。この道具では、人が置いた距離標から推定して出す |
| 起点からの距離 | この道具で、区間の中の位置を呼ぶための距離（m）。区間の起点から中心線に沿って測る。KP とは別のもの |
| 距離標 | 道路わきに立つ、道路の起点からの距離を示す標識 |
